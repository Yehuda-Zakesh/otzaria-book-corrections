# סיווג דיווחים ותיקונים מובנים באוצריא

נבדק ב־7 באוקטובר 2026 מול עותק אוצריא המקומי, commit `a68e30f09` (`SDK: feedback.submitBookCorrection עם אימות מקור והרשאת שליחה (#2017)`). זהו ממצא מהקוד המקומי, ולא אימות שהממשק כבר מופץ למשתמשים או שהאתר הפעיל תומך בו. החקירה מתארת את מצב גרסה 0.4.3; בעקבותיה מומש ב־0.1.0 מסלול v2 ישיר על ה־SDK הקיים של 0.9.98. [תיאור המימוש הנוכחי והמגבלות](legacy-reporting.md).

## מדוע התוסף מופיע כדיווח חופשי

`plugin/report.js:buildReport` שולח את חוזה הדיווח הישן: כותרת, טקסט נבחר ו־`error_details`. אין בו `schema_version`, `report_kind`, `correction`, `location` או `content_digest`. המילים "הצעת תיקון" בכותרת ובגוף הן טקסט לתצוגה, ולא סיווג מובנה. הוספת מראה מקום ב־0.4.3 לא משנה את הסיווג.

באוצריא עצמה `DirectErrorReportKind` מבחין בין `free_text` ל־`text_correction`. אין במודל קטגוריה נוספת של "תיקון שכבר הוחל". `ErrorReportHelper.buildDirectReport` בוחר `text_correction` רק כשיש מקור מאומת ואובייקט `TextCorrection`.

מקורות: `otzaria/lib/models/direct_error_report.dart:12,29,537,561`; `otzaria/lib/text_book/view/error_report_dialog.dart:259,700,1037`.

## מה אוצריא שולחת בדיוק

שני המסלולים משתמשים באותו יעד HTTP: `https://otzaria.org/api/reportingerrors`. ההבדל הוא המטען, ולא כתובת אחרת.

דיווח מובנה כולל את שדות הדיווח הרגילים וכן:

- `schema_version: 2`, `report_kind: "text_correction"`.
- `location`: אינדקס שורה אפסי, מזהה הספר המספרי במסד, מזהה בניית הספרייה ו־`he_ref` כשזמין. `line_number` לתצוגה נשאר מבוסס־1.
- `correction`: `original_line` הגולמי מהמסד, `original_selection`, `selection_offset` ביחידות UTF-16, `proposed_text`, `context_before`, `context_after`. בשינוי של שורה שלמה הבחירה והטווח הם null. הצעה ריקה היא מחיקה; null מציין שאין נוסח מוצע.
- `content_digest`: SHA-256 של JSON קנוני לפי `DirectErrorReport.contentDigest`, על שדות התוכן המוגדרים שם. אין לחשב גיבוב שרירותי של כל גוף הבקשה.
- `source_hint` ו־`client`.

נשמר גם בלוק לפני/אחרי ב־`error_details`, עבור שרת ישן. לכן קבלת HTTP 200 אינה ראיה שההצעה נשמרה כתיקון מובנה: אוצריא בודקת גם `correction_supported: true`. בלעדיו היא מסמנת שהשרת קיבל את ההצעה כטקסט בלבד.

מקורות: `otzaria/lib/models/direct_error_report.dart:166,207,537,540,561`; `otzaria/lib/utils/canonical_json.dart`; `otzaria/lib/services/direct_error_report_service.dart:519,531,605`.

## הממשק שכבר קיים בקוד אוצריא

`feedback.submitBookCorrection` כבר ממומש ונכלל בתיעוד ה־SDK. הוא דורש `feedback.send_email`; גרסת המינימום בטבלת התאימות ובתיעוד היא **0.9.99**. אין להסיק זמינות מכך ש־`pubspec.yaml` בעותק המקומי עדיין מציג 0.9.98.

בקשת תוסף לדוגמה:

```js
const result = await call('feedback.submitBookCorrection', {
  reportId: 'stable-id',
  bookId: 'שם הספר',
  bookUid: 'id:42',
  sectionIndex: 7,
  snapshots: [{ index: 7, text: 'לפני המקור אחרי' }],
  original: 'המקור',
  proposed: 'התיקון',
  sourceStart: 5,
  sourceEnd: 10,
  allowQueue: false
});
```

`call` כאן הוא עטיפת התוסף שמחלצת `data` מתשובת ה־SDK. הטווח מקומי לפסקת המקור לאחר ניקוי HTML, ולא היסט גלובלי בספר הערוך. הממשק מאמת את ה־snapshots מול המסד, ממפה את הטווח לשורה הגולמית, משיג מטא־דאטה וכתובת מייל מתוך אוצריא ובונה את חוזה v2. הוא אינו סומך על מזהה מסד, מייל או גרסת ספרייה שהתוסף ממציא.

נתמכים ספרי טקסט ממסד הספרייה הרשמי, ללא ספרים אישיים, מסדים מצורפים, קבצים חיצוניים או מהדורות חלופיות. עד 32 פסקאות בבקשה; `original` ו־`proposed` עד 20,000 יחידות UTF-16; גוף הדיווח עד 256 KiB.

התשובה היא `status: sent|queued`, מזהים, הודעה, `duplicate` ו־`correctionSupported`. השדה האחרון הוא null בתור. כאשר הוא false אין להציג למשתמש שהדיווח התקבל כתיקון מובנה. `allowQueue: false` משמר את בעלות התוסף על הניסיון החוזר. שגיאת `error.report_id_conflict` מחייבת מזהה חדש; כשל זמני משתמש באותו מזהה ובאותו תוכן.

מקורות: `otzaria/docs/plugin-sdk/API_REFERENCE.md:3274`; `otzaria/lib/plugins/bridge/plugin_bridge_adapter.dart:5654`; `otzaria/lib/plugins/services/plugin_book_correction_service.dart`; `otzaria/lib/plugins/services/plugin_extended_validator.dart:493`.

## מה הופך לתיקון מובנה ומה עדיין הופך לדיווח חופשי

| שינוי | התנהגות הממשק הקיים |
| --- | --- |
| החלפה או מחיקה בפסקה יחידה ללא HTML | תיקון מובנה כאשר הטווח תואם למקור |
| טקסט חוזר באותה פסקה | טווח מפורש מאפשר לבחור את המופע המדויק |
| הוספה בפסקה ללא HTML | תיקון של השורה השלמה כאשר נמסר טווח ריק מפורש והנוסח המלא עומד במגבלת האורך |
| טקסט בתוך תג HTML | תיקון מובנה רק כשההתאמה למקור הגולמי חד־משמעית ועוברת בדיקות הקשר |
| entity מפוענח או בחירה שחוצה תגיות | דיווח חופשי v2 כשהמיפוי אינו בטוח |
| שינוי שחוצה פסקאות | דיווח חופשי v2 |
| `forceFreeText: true` | דיווח חופשי v2 במכוון |

הענף הקיים `api/native-book-corrections` מכיל חיבור קודם לממשק. הוא בסיס שימושי, אך אינו תחליף לחיבור מחדש מול `main`: הוא כולל `forceFreeText` לחלקים מפוצלים, ומיפוי גבולות החלקים צריך בדיקה מול התיקונים החדשים. התיעוד הפעיל שטוען שכל ה־API "עתידי" אינו מעודכן ביחס לקוד אוצריא המקומי.

## מה אפשר לממש עכשיו ומה דורש הרחבה

1. **על אוצריא הכוללת את הממשק:** לחבר את התוסף ל־`feedback.submitBookCorrection`, להצהיר על ההרשאה ועל גרסת המינימום הנתמכת, להעביר snapshots וטווחים מדויקים, ולפרש את אישור הסיווג. לא צריך API נוסף לתיקונים רגילים בפסקה יחידה. אפשר לשמר את ממשק העריכה הנוכחי.
2. **על 0.9.98 המקורית:** אפשר עקרונית לבנות ולשלוח v2 ישירות דרך `network.fetchStream`, אם התוסף יכול לאמת את השורה הגולמית ואת מיפוי הטווח. `library.getBookContent` מחזיר טקסט גולמי כברירת מחדל, אבל זה תוכן ספר מחובר, ולא חוזה של שורת DB עם כל נתוני המיקום. `reader.getSectionTextMap` מספק מקור לאחר ניקוי HTML. לכן הנתונים הקיימים בעורך אינם מספיקים כדי לסמן כל שינוי כתיקון מובנה בבטחה. אפשר לבנות מסלול מוגבל לשורות שמיפוין הוכח, אך הדבר משכפל את אימות המקור, בניית v2 ומטא־דאטה של אוצריא. החיבור לממשק הקיים עדיף; הוא עדיין תלוי בבנייה שתומכת בו ובשרת שתומך ב־v2.
3. **כדי שכל עריכת ספר תגיע כהצעה מובנית:** צריך להרחיב את המודל ואת חוזה האתר לשינוי רב־פסקאות/אוסף פעולות, ולהרחיב את הממשק הקיים בהתאם. המודל הנוכחי של `TextCorrection` מכיל שורה אחת. שינוי שם הקטגוריה לבדו אינו הופך שינוי רב־פסקאות לתיקון שניתן להחלה.
4. **כדי לאפשר למנהל להחיל תיקון בפועל:** נדרש מסלול אישור והחלה באתר/במערכת ניהול מקור הספרייה, עם בדיקת שהמקור עדיין תואם לדיווח. מסלול השליחה באוצריא שנבדק אינו כותב לספר ואינו מעניק לתוסף הרשאת כתיבה. לא נבדק קוד האתר או כלי המנהל, ולכן אין להסיק שהאפשרות הזו חסרה אצלם.

הרחבה שימושית של אותו API, אם רוצים למנוע סיווג חופשי בלי ידיעת התוסף: פרמטר `requireStructured: true` שיחזיר שגיאה לפני שליחה אם אי אפשר לייצר תיקון מובנה, ותשובה עם `reportKind` ו־`fallbackReason` שמבדילה בין טווח לא נתמך לבין שרת ללא תמיכת תיקונים. זו הצעה חדשה, לא יכולת קיימת. לשיפור תמיכה ב־HTML אפשר להוסיף מיפוי טווח מדויק לטקסט הגולמי בתוך השירות הקיים; אין הכרח לחשוף API נפרד לקריאת DB.

## היקף האימות

נבדקו המודל, דיאלוג הדיווח, שירות השליחה, מימוש ה־SDK, טבלאות הרשאות ותאימות, תיעוד ומבחני הממשק. הורצו ארבעה קובצי בדיקות באוצריא: `plugin_book_correction_service_test.dart`, `direct_error_report_text_correction_test.dart`, `direct_error_report_service_test.dart`, `plugin_bridge_book_correction_api_test.dart`; כל 103 הבדיקות עברו. לא נשלחו דיווחים אמיתיים, לא נבדקה גרסה מותקנת אצל המנהל, ולא נבדק קוד האתר. החקירה אינה משנה עיצוב או התנהגות ממשק ולכן אינה כוללת בדיקת דפדפן חדשה.
